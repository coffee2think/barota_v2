# 서울시 지하철 Android 앱 기술 선택 보고서

- 작성일: 2026-09-15
- 목표: 출발역과 도착역을 선택하는 Android 앱의 기본 화면을 빠르고 안정적으로 구현한다.
- 배포 범위: 우선 개인 기기와 포트폴리오 시연용 APK로 개발하되, 향후 Play 스토어 운영 가능성을 고려한다.

- 앱 이름: 지하철 바로타
- 개발자 표시 이름: 길빛 스튜디오(Gilbit Studio)
- 애플리케이션 ID: `com.gilbit.barota`

## 2. 검토한 대안과 결정 근거

### 2.1 앱 개발 방식

선택: Kotlin + Jetpack Compose 기반 Android 네이티브

- 선택 이유: Android 전용 앱이며 테스트 기기도 Android 한 대다. Google이 권장하는 최신 Android UI 도구를 직접 사용하므로 기기 기능 연동과 문제 해결 경로가 단순하다.
- Flutter: 하나의 코드로 여러 플랫폼을 지원하지만 iOS 확장 계획이 없어 Dart 학습과 플랫폼 계층 도입의 이점이 작다.
- React Native: React 및 TypeScript 경험이 있을 때 유리하지만 현재 Java/Spring 경험과의 연결성이 Kotlin보다 낮고 네이티브 모듈 호환성 관리가 추가된다.

### 2.2 앱 구조와 상태 관리

선택: MVVM + ViewModel + StateFlow

- 선택 이유: 화면 표시와 비즈니스 규칙을 분리하면서도 초기 코드량이 지나치게 많지 않다. Spring의 계층 분리 경험을 활용하기도 쉽다.
- 단순 Compose 로컬 상태: 첫 화면은 빨리 만들 수 있지만 API와 화면이 추가되면 상태와 로직이 UI에 섞이기 쉽다.
- MVI: 상태 변화가 엄격하고 명확하지만 작은 초기 기능에 필요한 이벤트 및 리듀서 코드가 과도하다.

### 2.3 API 호출 위치

선택: 초기 APK는 앱에서 직접 호출하고, 공개 운영 전 Spring Boot 프록시로 전환

- 선택 이유: 현재는 서버 배포 없이 빠르게 시연할 수 있다. 데이터 계층에 Repository 인터페이스를 두어 나중에 호출 대상을 백엔드로 교체한다.
- 처음부터 Spring Boot 프록시 사용: 인증키 보호, 캐시, 요청 제한 관리에는 가장 좋지만 초기 서버 개발과 배포 시간이 추가된다.
- 서버리스 함수: 서버 운영 부담은 작지만 새로운 클라우드 환경 학습이 필요해 현재 개발 속도 목표와 맞지 않는다.

주의: 로컬 설정 파일에서 주입한 인증키도 빌드된 APK에서는 완전히 숨길 수 없다. 서울시 실시간 지하철 API는 인증키가 필요하고 기본 호출 제한이 있으므로 공개 배포 전에는 반드시 서버 측 프록시, 캐시 및 호출 제한 정책을 적용한다.

### 2.4 네트워크 라이브러리

선택: Retrofit + OkHttp

- 선택 이유: 인터페이스 기반 API 정의가 Java/Spring 경험자에게 익숙하며 로깅, 타임아웃, 오류 처리를 붙이기 쉽다.
- Ktor Client: Kotlin 중심 API와 멀티플랫폼에는 유리하지만 Android 전용 프로젝트에서는 추가 학습 대비 이점이 작다.
- HttpURLConnection: 외부 의존성이 없지만 요청, 스레드, 오류 및 응답 처리를 직접 구현해야 해 생산성과 유지보수성이 낮다.

### 2.5 JSON 직렬화

선택: kotlinx.serialization

- 선택 이유: Kotlin 공식 생태계에 속하며 컴파일 타임에 직렬화 코드를 생성한다. `ignoreUnknownKeys` 설정으로 외부 API의 필드 추가에도 대응할 수 있다.
- Moshi: Kotlin 지원이 우수하고 Retrofit과 잘 연동되지만 별도 KSP 또는 리플렉션 설정이 필요하다.
- Gson: Java 경험자에게 익숙하지만 현재 유지보수 모드이며 Kotlin null 안정성과 데이터 클래스 지원이 상대적으로 약하다.

### 2.6 의존성 주입

선택: Hilt

- 선택 이유: Android 공식 권장 라이브러리이며 Retrofit, Repository, ViewModel의 생성 관계를 컴파일 시 검증한다. 향후 화면이 늘어날 때 수동 연결 코드를 줄인다.
- 수동 의존성 주입: 한 화면에서는 단순하지만 화면과 생명주기 범위가 늘어날수록 객체 생성 코드가 증가한다.
- Koin: Kotlin DSL로 빠르게 구성할 수 있지만 잘못된 구성 일부가 런타임에 발견될 수 있고 공식 Android 표준 측면에서는 Hilt보다 약하다.

### 2.7 최소 지원 Android 버전

선택: minSdk 26(Android 8.0)

- 선택 이유: 테스트 기기 Android 16에서 충분히 검증할 수 있고, 오래된 버전을 위한 분기와 호환 코드 부담을 줄인다.
- API 23(Android 6.0): 지원 기기는 늘지만 단일 최신 기기로 개발하는 현재 상황에서 호환성 검증 비용이 커진다.
- API 28(Android 9.0): 호환성 부담은 조금 줄지만 API 26과 비교해 개발 이점은 작고 지원 범위만 감소한다.

`compileSdk`는 최신 안정 AndroidX 요구사항에 맞춰 37을 사용한다. 실제 동작 기준인 `targetSdk`는 테스트 기기의 Android 16에 맞춰 36을 사용한다.

### 2.8 역 선택 방식과 데이터

선택: 앱 내부 정적 JSON + 검색 가능한 역 선택 바텀시트

- 선택 이유: API 장애와 호출 제한 없이 역 검색이 즉시 동작한다. 역명과 호선을 함께 표시해 동명역과 환승역을 구분할 수 있다.
- 화면 내 자동완성 입력: 조작 단계는 적지만 두 입력창, 키보드, 추천 목록의 포커스 관리가 복잡하다.
- 노선도 선택: 시각적으로 직관적이지만 확대, 이동, 환승역, 접근성 처리 때문에 초기 개발 범위를 크게 늘린다.

초기 화면 검증에는 대표 역 61개로 구성한 프로토타입 JSON을 사용한다. API 연동 단계에서 서울시 또는 서울교통공사의 공식 전체 데이터로 교체하고 출처와 기준일을 함께 관리한다. 실제 운영 시에는 앱 업데이트 또는 서버 동기화 방식으로 갱신한다.

### 2.9 첫 화면 기능 범위

선택: 표준형

- 출발역 선택
- 도착역 선택
- 출발역과 도착역 맞바꾸기
- 동일한 역 선택 방지
- 두 역이 선택되기 전까지 조회 버튼 비활성화
- 선택 완료 후 다음 화면으로 이동할 수 있는 기본 동작

대안인 최소형은 완성도가 낮고, 최근 검색·즐겨찾기·주변 역까지 포함하는 확장형은 로컬 저장소와 위치 권한을 추가해 초기 개발 속도를 떨어뜨린다.

### 2.10 디자인 시스템

선택: 안정 버전 Material 3 기반의 가벼운 커스터마이징

- 선택 이유: Compose용 컴포넌트, 테마, 다크 모드와 접근성 기반을 제공하며 Android 16 시스템 UI와 잘 어울린다.
- Material 3 Expressive: 최신 표현력은 좋지만 실험 단계 API 사용 가능성이 있어 안정성 목표와 맞지 않는다.
- 완전한 커스텀 디자인 시스템: 독창성은 높지만 기본 컴포넌트부터 설계해야 해 개발 시간이 증가한다.

### 2.11 화면 이동

선택: 안정 버전 Navigation Compose

- 선택 이유: Compose 화면 간 이동, 뒤로가기, 상태 복원과 Hilt ViewModel 범위를 검증된 방식으로 관리할 수 있다.
- Navigation 3: Compose 중심의 최신 구조지만 생태계 전환기 기술을 도입하는 부담이 있다.
- 상태만으로 화면 전환: 한 화면에서는 단순하지만 결과 화면이 추가되면 뒤로가기와 상태 복원을 다시 설계해야 한다.

### 2.12 테스트 전략

선택: 핵심 균형형

- ViewModel 단위 테스트: 역 선택, 동일 역 방지, 맞바꾸기, 조회 버튼 상태를 검증한다.
- Compose UI 테스트: 바텀시트 열기, 역 검색과 선택, 버튼 활성화 등 핵심 흐름을 검증한다.
- Fake Repository: 네트워크 없이 성공과 실패 상태를 재현한다.
- API 연결 단계: MockWebServer를 추가해 JSON 변환과 HTTP 오류 처리를 검증한다.

최소 테스트형은 UI 연결 오류를 놓칠 수 있다. 모든 계층의 통합 및 전체 시나리오를 포함하는 포괄형은 현재 범위에 비해 설정과 유지 비용이 크다.

## 3. 초기 구현 원칙

1. UI는 상태를 표시하고 사용자 이벤트를 ViewModel에 전달한다.
2. ViewModel은 Android UI 객체를 참조하지 않으며 `StateFlow`로 단일 화면 상태를 제공한다.
3. 데이터 접근은 Repository 인터페이스 뒤에 숨겨 정적 데이터, 서울시 API, 향후 Spring Boot 프록시를 교체할 수 있게 한다.
4. API DTO와 화면에서 사용하는 도메인 모델을 분리한다.
5. 서울시 인증키는 버전 관리에서 제외하고 빌드 설정으로 주입한다.
6. 안정 버전 의존성을 우선하고 실험 단계 API 사용을 최소화한다.
7. 접근성 레이블, 충분한 터치 영역, 다크 모드와 시스템 뒤로가기를 기본 요구사항으로 취급한다.

## 4. 구현 예정 구조

```text
UI (Compose Screen / Bottom Sheet)
        ↓ event        ↑ UiState
ViewModel (StateFlow)
        ↓
StationRepository interface
        ├─ BundledStationRepository (앱 내부 역 JSON)
        └─ SeoulSubwayRepository (Retrofit, 추후 Spring Boot 주소로 교체)
```

이 구조는 첫 화면을 작게 시작하면서도 실시간 지하철 조회 화면과 운영용 백엔드를 추가할 수 있도록 경계를 유지한다.
