# 2026-09-18 — 상·하행 판정 구현 계획

상태: 구현 전 계획 수립. 앱 방향 판정 코드는 아직 변경하지 않았다.

## 요구사항과 범위

사용자 요청: 기존 `2026-09-18-arrival-mvp-fix-tasks.md`를 참조해 출발역에서 목적지로 진행하는 방향을 판별하고 실제 도착 열차에 적용한다. 지정 인수 경로는 **독산 → 종로3가**이며 역전 경로도 검증한다. 이번 요청은 T01~T03의 방향 기능이며 T04 예상 진입 정렬, T05 시간표 완전성, T06 색상·디버그 개선 및 지연 공지는 별도 범위다. 방향 연결에 필요한 상태 초기화와 이전 요청 취소는 포함한다.

역 목록은 앞선 별도 작업에서 제공 CSV 기준으로 이미 갱신됐다. 기존 계획의 역 목록 교체 보류는 이전 시점의 기록으로 보존하며 이번 방향 구현에서 다시 교체하지 않는다.

## 현재 확인한 사실

- `SeoulArrivalRepository.getArrivals`는 출발역 이름만 필터링하고 상·하행을 혼합해 표시한다. 방향 필터 없이 모든 열차의 정차 시간표를 조회한다.
- 실시간 DTO에는 노선 `subwayId`, 방향 `updnLine`이 있다. 기존 도메인 변환은 방향이 비면 행선 문자열로 대체하므로 필터 판단에는 원본 필드를 사용해야 한다.
- 선택 화면에서 도착 화면으로 양쪽 역의 노선 목록을 전달하지만 Repository에는 이름 두 개만 전달한다.
- 선택용 `stations.json`의 정렬과 ID는 철도 진행 순서를 뜻하지 않는다.
- 제공 CSV의 1호선 외부코드는 독산 P143, 가산디지털단지 P142, 구로 141, 신도림 140, 영등포 139, 신길 138, 대방 137, 노량진 136, 용산 135, 남영 134, 서울역 133, 시청 132, 종각 131, 종로3가 130이다. 이 숫자를 전체 노선의 방향 공식으로 사용하지 않는다.
- 실제 API fixture와 사용자 기기의 운행 화면은 아직 확보하지 않았다. 예상 테스트 응답은 합성 fixture로 명시한다.
- 이전 빌드 시도에서 `android-37.0` SDK가 없어 테스트/빌드가 실행되지 않았다. 검증 환경은 구현 시 다시 확인한다.

## 구현 순서

### 1. 방향 근거 및 지원 계약 확정 (T01/T02)

서울시 API 문서와 운영기관의 노선·운행 정보를 대조해 독산에서 가산디지털단지·구로·서울역을 거쳐 종로3가로 가는 방향이 1호선 상행임을 확인한다. 역전 경로는 하행이다. 실제 응답 접근이 가능하면 키를 출력하거나 fixture에 포함하지 않고 노선/방향 값만 검증한다. 응답을 확보하지 못하면 합성 fixture와 실제 응답 미검증을 구분한다.

지원 메타데이터는 선택 역 데이터와 분리한다. 지정 경로와 중간역을 포함하는 검증된 1호선 구간을 우선 정의하며, 추가 구간은 근거가 확보된 경우에만 확장한다. 한 경로의 성공으로 24개 노선 전체가 지원된다고 주장하지 않는다. 지선·분기·환승 경로는 역 코드 대소 비교로 추정하지 않는다.

공통 노선이 여러 개면 명시적 노선 선택이 필요하다. 순환선은 내선/외선을 상행/하행과 별도 타입으로 유지하고 근거 있는 방향 선택만 허용한다. 지원되지 않은 노선 또는 구간은 안내 상태로 처리하며 임의 방향이나 무필터 목록으로 대체하지 않는다.

근거 확인 대상:

- 서울시 실시간 도착정보: https://data.seoul.go.kr/dataList/OA-12764/A/1/datasetView.do
- 서울시 실시간 위치정보의 방향 코드 설명은 별도 서비스이므로 도착정보에 그대로 전용하지 않는다: https://data.seoul.go.kr/dataList/datasetView.do?infId=OA-12601&serviceKind=1&srvType=A
- 운영기관 노선도/시각표 및 제공 CSV의 역·노선 정보.

### 2. 순수 방향 판정기 구현 (T03)

`RouteDirectionResolver`를 Android/API와 독립된 순수 Kotlin 코드로 만든다. 검증된 메타데이터에서 출발역·목적지역·선택 노선으로 `상행`, `하행`, `내선`, `외선`을 판단한다. 역명 정규화는 명시적인 별칭만 사용하며 모든 역명의 마지막 `역`을 무조건 제거하지 않는다.

결과 계약은 `방향 확정`, `노선/방향 선택 필요`, `미지원`, `판정 불가`를 구분한다. 같은 역, 공통 노선 없음, 메타데이터 누락도 정상 방향으로 취급하지 않는다. API의 알 수 없거나 빈 방향 값은 매칭하지 않고, 행선지 문자열·정차 여부로 방향을 복원하지 않는다.

### 3. 실제 조회 및 화면 연결 (T03)

- 선택 노선과 판정 결과를 조회 상태에 연결한다. 이름 외에 이미 탐색 인자로 전달되는 노선 목록을 사용한다.
- 출발역, 선택 노선 ID, API 방향을 먼저 필터링한 뒤 도메인 변환과 정차 시간표 조회를 수행한다.
- 같은 방향이지만 목적지에 정차하지 않는 열차는 유지한다. 구로 종착 같은 단거리 운행을 목적지에 도달하지 않는다는 이유로 방향 필터에서 제거하지 않는다.
- 반대 방향·다른 노선·알 수 없는 방향 열차에는 정차 API를 호출하지 않는다.
- 화면에 선택/확정된 노선·방향을 표시하고, 판정 불가/미지원/추가 선택 필요와 정상 조회 후 열차 없음 문구를 구분한다.
- 경로/선택 변경 시 이전 목록을 초기화하고 이전 요청을 취소하거나 식별해 늦은 응답이 새 경로를 덮어쓰지 않게 한다. 코루틴 취소를 일반 조회 실패로 감추지 않는다.

### 4. 검증

순수 판정기 테스트:

- 독산 → 종로3가: 1호선 상행.
- 종로3가 → 독산: 1호선 하행.
- 지정 경로의 중간역 및 별칭 `독산역` 입력.
- 같은 역, 메타데이터 누락, 공통 노선 없음, 다중 공통 노선, 순환선 내외선의 독립성, 미지원 분기.

Repository 통합 테스트:

- 합성 혼합 응답에서 1호선 상행만 남고 역전 조회에서 하행만 남는다.
- 빈 방향/모르는 방향/다른 노선/다른 출발역은 제외한다.
- 같은 방향의 목적지 미정차 열차도 유지한다.
- 제외된 열차의 정차 API 호출 횟수는 0이다.
- 정상 방향 조회 결과 없음과 경로 판정 실패를 구분한다.

ViewModel/UI 연결 테스트:

- 선택/판정 상태와 방향 안내, 노선 선택 변경, 경로 맞바꾸기 및 이전 요청 응답 역전.
- 기존 조회/새로고침 테스트 회귀.

가능한 환경에서 `testDebugUnitTest`, `compileDebugAndroidTestKotlin`, `lintDebug`, `assembleDebug`를 실행한다. 연결 기기가 있을 때만 실제 Compose/실기기 검증을 수행한다. SDK 등 환경 문제로 실행하지 못한 검증을 성공으로 기록하지 않는다. 필요하면 순수 Kotlin 로직을 별도 실행 가능한 환경에서 검증하되 APK/전체 테스트 통과를 대체했다고 주장하지 않는다.

## 완료 기준

지정 경로에서 상행 판단이 화면 및 실제 조회 파이프라인에 연결되고, 혼합 방향 응답의 하행 열차가 정차 조회 전에 제외되며, 역전 시 하행으로 전환되는 테스트 증거가 있어야 한다. 지원 범위와 미지원/선택 필요 상태가 명시돼야 한다. 검증 결과 및 제약을 새 개발 기록으로 남긴다. 실제 API/실기기 검증이 없다면 그 부분은 미검증으로 남긴다.

## 구현 후 업데이트

위 계획을 먼저 작성한 뒤 방향 기능을 구현했다. 독산 → 종로3가 상행 및 역전 하행, 실제 혼합 응답의 방향 필터와 정차 조회 순서, 노선 선택/미지원/판정 불가 상태 연결을 검증했다. 실제 API로 지원 구간의 방향을 대조했고 자동 테스트 39개, UI 테스트 컴파일, Lint(오류 0, 기존 경고 2개), APK 빌드가 통과했다. 지원 범위는 검증된 1호선 종로3가–독산 구간이며 다른 구간과 내외선/지선은 명시적인 미지원 안내다. 연결 기기가 없어 Compose 실행과 스마트폰 인수는 미실행이다. 자세한 결과와 SDK 환경 우회/설정 복원은 [개발 기록](../development-log/2026-09-18-route-direction-implementation.md)을 참조한다.
