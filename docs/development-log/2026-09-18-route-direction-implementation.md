# 2026-09-18 — 상·하행 판정 및 도착 열차 필터 구현

## 1. 배경 / 문제

사용자가 기존 MVP 태스크를 참조해 상·하행 판정을 구현하고 독산 → 종로3가로 테스트하도록 요청했다. 먼저 별도 구현 계획과 계획 기록을 작성한 뒤 구현을 시작했다. 기존 Repository는 상·하행을 혼합해 표시하며 제외할 열차도 정차 시간표를 조회했다.

## 2. 검토한 선택지

- 선택용 역 JSON의 배열/ID나 외부코드 대소 비교로 방향 추정: 운행 순서·분기를 보장하지 않아 제외했다.
- 행선지 문자열 또는 목적지 정차 여부로 방향 추정: 미정차 열차를 숨기거나 빈 방향을 임의 복원하므로 제외했다.
- 실제 응답으로 검증한 최소 구간의 명시적인 운행 순서와 순수 판정기: 제공 CSV의 역·노선 정보와 실제 API의 방향/방면을 대조할 수 있어 채택했다.
- 다중 공통 노선 자동 선택: 다른 노선으로 잘못 조회할 수 있어 명시적 선택으로 처리했다.

## 3. 결정 및 근거

이번 요청은 방향 기능(T01~T03)에 집중한다. 기존 정렬·시간표 완전성·색상·디버그 개선(T04~T06), 전체 노선망/환승 탐색, 지연 공지는 구현하지 않는다. 계획의 최소 방향 메타데이터 계약에 따라 **1호선 종로3가–독산 14개 역 사이의 직통 진행 방향**을 지원한다. 해당 구간 내 서로 다른 182개 역쌍의 방향을 판별한다. 24개 노선 전체가 지원된다고 주장하지 않으며 다른 구간·노선·순환선·지선은 명시적인 미지원 안내로 처리한다.

### 실제 조회 근거 (2026-09-18)

서울시 `realtimeStationArrival`을 읽기 전용으로 조회했다. 키는 URL 조합에만 사용하고 출력·fixture·문서에 포함하지 않았다. 독산의 실제 응답은 `INFO-000`이며 1호선 `1001`, 가산디지털단지 방면 `상행`, 금천구청 방면 `하행`을 확인했다.

종로3가, 종각, 시청, 서울(API 명칭), 남영, 용산, 노량진, 대방, 신길, 영등포, 신도림, 구로, 가산디지털단지의 응답도 조회해 모두 `INFO-000`을 확인했다. 다음 구간의 방향/방면을 실제 응답에서 확인했다:

- 종로3가의 하행은 종각 방면, 종각의 상행은 종로3가 방면.
- 종각 → 시청 → 서울 → 남영 → 용산 → 노량진 → 대방 → 신길 → 영등포 → 신도림 → 구로는 하행이며 반대 방면은 상행.
- 가산디지털단지의 상행은 구로 방면, 하행은 독산 방면.
- 독산의 상행은 가산디지털단지 방면.
- 구로 응답에는 인천 계통의 구일 방면 하행도 있다. 따라서 종로3가 → 독산 조회에서 하행의 인천 계통을 방향 필터로 숨기지 않는다. 목적지 정차 여부는 기존 별도 판정기에 맡긴다.

위 명시적인 하행 순서는 제공 CSV의 종로3가 130부터 독산 P143까지 역명·노선 정보와도 대조했다. 숫자 계산으로 순서를 생성하거나 분기 방향을 일반화하지 않았다. 행선지에 모순처럼 보이는 실제 항목도 있었으므로 런타임 필터는 행선지가 아니라 원본 `updnLine`을 사용한다.

서비스 문서: https://data.seoul.go.kr/dataList/OA-12764/A/1/datasetView.do

위치정보 서비스의 0/1 방향 코드는 다른 API의 계약이므로 도착정보 필터에 전용하지 않는다. 도착정보에서 확인한 문자열 `상행`/`하행`을 사용하고 `내선`/`외선`은 별도 내부 타입으로 유지한다. 빈 값·미지 값·다른 방향 계열은 임의 매칭하지 않는다.

## 4. 구현 내용

- `domain/RouteDirectionResolver.kt`: 순수 판정기, 명시적인 14개 역 운행 순서, 방향 타입, 확정/노선 선택 필요/미지원/판정 불가 결과. 실제 지원 역에 한해 `독산역` 같은 접미 별칭을 정규화하고 서울/서울역을 명시적으로 대응한다.
- `ArrivalRepository.kt`: 확정된 노선 ID·방향·정규화된 경로를 받도록 계약 변경. 이름 두 개만 받아 무필터 조회하는 경로를 제거했다.
- `SeoulArrivalRepository.kt`: 출발역 → 노선 ID → 원본 방향 필터 후 도메인 변환/정차 시간표 조회. 같은 방향의 목적지 미정차 열차는 유지한다. `INFO-200`은 정상 빈 결과이며, 방향값을 해석할 수 없어 조회 결과를 결정할 수 없는 경우는 별도 오류다. 개별 정차 API 실패는 기존 UNKNOWN 동작을 유지하되 코루틴 취소는 전파한다.
- `AppModule.kt`: 실시간 API 키를 Named 주입으로 분리해 Repository 통합 테스트에 실제 키가 필요하지 않게 했다.
- `ArrivalViewModel.kt`: 탐색 인자의 양쪽 노선 목록을 판정에 연결, 노선 선택/새로고침 상태 유지, 경로·선택 변경 시 목록 초기화, 기존 요청 취소와 요청 세대 식별로 응답 역전 방지.
- `ArrivalScreen.kt`: 확정 노선·방향 안내 및 공통 노선 선택 버튼. 미지원/판정 불가/선택 필요와 정상 빈 결과를 구분하며 미지원 상태를 무필터 목록으로 대체하지 않는다.
- `doksan-arrivals-2026-09-18.json`: 독산 실제 API 응답 8개 열차의 필요한 필드만 담은 fixture. 실제 방향 응답을 검증하지만 목적지 정차 사실이나 실제 진입 순서를 보장하는 fixture는 아니다.
- 순수 판정기/Repository/ViewModel/UI 회귀 테스트 및 README 지원 범위 안내를 추가했다.

## 5. 검증 결과

검증 진행 중. 실제 API의 구간 방향 대조 및 fixture 확보는 완료했다. 자동 테스트·Lint·APK 빌드의 최종 결과는 완료 후 아래에 추가한다.

환경 확인에서 SDK 플랫폼이 없음을 재확인했고 기존 라이선스를 사용해 `android-37.0` 플랫폼을 설치했다. 이후 Kotlin 앱 컴파일은 통과했으나 Java 컴파일에서 기존 SDK `core-lambda-stubs.jar`의 ZipFileSystem 종료 중 접근 오류가 발생했다. 프로젝트의 버전 설정과 원본 SDK를 바꾸지 않고 동일 SDK의 작업 영역 복사본으로 검증을 이어가는 중이다.

ADB 연결 목록 조회는 통과했으며 연결된 기기가 없다. Compose 테스트 실행 및 사용자 스마트폰 인수 검증은 아직 수행하지 않았다. UI 테스트 컴파일을 실행 성공과 혼동하지 않는다.

## 7. 자동 검증 완료 업데이트

위 검증 진행 상태 이후 다음 결과를 확인했다.

- `testDebugUnitTest`: 39개 테스트, 실패 0, 오류 0. 판정기 6개 테스트에 지원 구간 182개 역쌍 검증을 포함한다. Repository 11개 테스트는 실제 독산 혼합 응답, 합성 역전 응답, 미정차 열차 유지, 제외 열차의 정차 요청 미호출, 방향 해석 불가와 정상 빈 결과 구분, 취소 전파 등을 검증했다. ViewModel 9개 테스트는 노선 선택·새로고침과 서로 다른 경로/같은 경로의 늦은 응답 방지를 검증한다. 나머지 13개 기존 정차/역 선택/역 자산 테스트도 통과했다.
- `compileDebugAndroidTestKotlin`: 통과. 새 방향 안내/노선 선택/미지원 안내 Compose 테스트 3개를 포함한다. 실제 UI 테스트 실행은 하지 않았다.

- 네 명령을 함께 실행한 마지막 Gradle 호출은 `BUILD SUCCESSFUL`이었다. 앞선 개별 실행에서 실제 테스트 실행과 강제 Lint 재분석을 수행한 뒤 마지막 호출에서는 대부분 UP-TO-DATE로 재확인했다.

환경 오류를 무시하거나 프로젝트 SDK/의존성 버전을 낮추지 않았다. 원본의 `android-37.0` 플랫폼과 `36.0.0` 빌드 도구를 `.gradle-user/route-direction-sdk`로 복사하고 `local.properties`의 SDK 경로만 검증 동안 임시 지정했다. 플랫폼 android.jar와 core-lambda-stubs.jar의 SHA-256이 원본과 일치함을 확인했다. `--no-daemon`과 `-Pkotlin.compiler.execution.strategy=in-process`로 SDK 파일 핸들/컴파일러 사용자 경로 문제를 분리했다. 검증이 끝난 뒤 SDK 경로를 원래 값으로 복원했고 API 키와 다른 로컬 설정은 변경하지 않았다.

재현용 검증 명령(동일 SDK 복사본 경로를 임시 지정한 상태):

```powershell
$env:ANDROID_USER_HOME = Join-Path $PWD '.gradle-user/android-user'
.\gradlew.bat --no-daemon --offline --gradle-user-home .gradle-user '-Pkotlin.compiler.execution.strategy=in-process' testDebugUnitTest compileDebugAndroidTestKotlin lintDebug assembleDebug
```

작업 영역 SDK 복사본에는 platform-tools가 없어 해당 환경 경고가 있었고, Android metrics 사용자 설정 경로 경고도 있었다. 이들은 앱 코드의 신규 Lint 오류가 아니다. 원본 SDK에서 일반 빌드가 이 실행 환경의 ZipFileSystem 접근 문제 없이 동작하는지는 확인하지 못했으며, 같은 문제가 재발하면 위 동일 SDK 복사본 방식이 필요하다.

자동 검증 및 결과 기록은 완료했다. 연결된 기기가 없어 `connectedDebugAndroidTest` 및 사용자 스마트폰 인수는 미실행으로 남긴다. 다른 구간·노선 확장 및 전체 MVP의 T04~T08 완료를 뜻하지 않는다.
