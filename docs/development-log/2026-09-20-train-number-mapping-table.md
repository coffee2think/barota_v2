# 실시간-시간표 열차번호 매핑 테이블 도입

## 1. 배경 / 문제

실시간 도착정보 API의 `btrainNo`와 시간표 API의 `trainno`는 노선과 운행 서비스에 따라 표기 방식이 다르다. 기존 구현은 실시간 번호의 선행 0을 제거한 뒤 `K`, `S` 접두어만 순서대로 붙였기 때문에 1호선 일부 열차 외에는 시간표를 찾지 못했다. 4호선처럼 `4178`과 `S4178`이 동시에 존재하는 경우에는 숫자 부분만 같고 실제 종착역과 운행시각이 다른 열차를 선택할 가능성도 있었다.

이미 확인한 대응을 매번 다시 탐색하지 않고 재사용하면서, 시간표 개편 등으로 잘못된 매핑이 남았을 때 자동으로 복구할 수 있는 저장 구조가 필요했다.

## 2. 검토한 선택지

* 노선별 접두어·접미어 규칙을 코드의 `if/else`로 추가하는 방법은 구현은 단순하지만 새로운 운행 서비스가 추가될 때마다 앱 코드를 수정해야 하고, 같은 숫자 본체를 공유하는 서로 다른 열차를 구분하지 못한다.
* JSON 자산에 매핑을 미리 작성하는 방법은 초기 데이터에는 적합하지만 런타임에 새로 발견한 매핑을 앱이 추가할 수 없다.
* 앱 내부 SQLite 테이블에 검증된 매핑을 저장하는 방법은 런타임 갱신과 영구 재사용이 가능하고 별도 라이브러리를 추가하지 않아도 된다.

## 3. 결정 및 이유

Android 기본 SQLite에 `train_number_mappings` 테이블을 만들고 저장 접근은 `TrainNumberMappingStore` 인터페이스로 분리했다.

매핑 키는 `btrainNo` 하나가 아니라 다음 문맥을 함께 사용한다.

* 시간표 노선명
* 정규화한 실시간 열차번호
* 방향
* 정규화한 종착역
* 열차 종류
* 평일/주말 구분

같은 숫자 본체를 가진 시간표 열차가 여러 개 존재할 수 있으므로 문맥 없는 전역 매핑은 안전하지 않다고 판단했다.

## 4. 구현 내용

* `TrainNumberMapping`, `TrainNumberMappingKey`, `TrainNumberMappingStore`를 추가했다.
* `SqliteTrainNumberMappingStore`가 복합 기본키 기반 조회, upsert, 삭제를 담당한다.
* 목적지 정차 판정 전에 매핑 테이블을 우선 조회한다.
* 저장된 번호가 현재 출발역 시간표와 종착역 또는 예상 통과시각에 맞지 않으면 오래된 매핑으로 판단하여 삭제한다.
* 매핑이 없으면 출발역 시간표를 열차번호 조건 없이 조회하고, `trainno`에서 추출한 숫자 본체가 정규화된 `btrainNo`와 같은 후보를 찾는다.
* 후보가 여러 개면 종착역 일치를 우선하고, 여전히 여러 개이면 실시간 예상 도착시각과 시간표 출발시각의 차이를 비교한다. 동률이거나 1시간 이상 차이 나는 불확실한 후보는 저장하지 않는다.
* 검증된 후보만 매핑 테이블에 저장하고 목적지역 시간표 조회에 사용한다.
* 동일 출발역·노선·방향·날짜의 탐색용 전체 시간표는 메모리에서 공유하여 여러 미등록 열차가 동시에 들어와도 전체 시간표 API를 반복 호출하지 않도록 했다.
* 시간표 전체 건수가 1,000건을 넘으면 `1001/2000`처럼 다음 범위를 이어서 조회한다. 실제 1호선 종로3가 하행 주말 시간표가 총 1,278건임을 확인해 이 처리를 추가했다.
* K/S 접두어 하드코딩과 노선별 분기 없이 숫자 본체·종착역·시각을 이용하므로 숫자형, `K472`, `3014K`, `E9679` 형식을 같은 흐름으로 처리한다.

## 5. 검증 결과

`testDebugUnitTest` 전체 실행 결과:

* 테스트 스위트 7개
* 테스트 65개
* 실패 0개
* 오류 0개
* 건너뜀 0개

추가 검증 범위에는 캐시 우선 조회, 신규 매핑 저장, 다음 조회에서 재사용, 숫자형·접두어·접미어 탐색, 4호선 동일 숫자 충돌의 종착역 판별, 시각 기반 판별, 동률 후보 미저장, 오래된 캐시 삭제 후 재탐색, 동일 출발역 탐색 시간표 공유, 1,000건 초과 페이지 조회, API 오류 시 미저장이 포함된다.

실제 기기에서 SQLite 파일 생성과 앱 재시작 후 매핑 유지 여부는 아직 검증하지 않았다.

## 6. 남은 작업 / 보류 사항

* 실제 기기에서 1~9호선 표본을 대상으로 최초 탐색과 앱 재시작 후 캐시 재사용을 확인한다.
* 종착역 명칭이 API 간에 다르게 표기되는 사례가 확인되면 역 별칭 데이터를 노선 자산에 추가한다.
