# 런타임 열차번호 fallback 및 배치 정차 판정

## 1. 배경 / 문제

실기기 테스트에서 정적 `btrainNo → trainno` 매핑에 없는 열차가 자주 `UNKNOWN`으로 남아 정차·미정차를 제대로 구분하지 못했다. 기존 앱은 배포 시점의 JSON 매핑만 읽고, 매핑이 없거나 시간표 개편으로 값이 달라진 경우 런타임에 복구하지 않았다.

## 2. 검토한 선택지

* 정적 JSON만 갱신하는 방식은 모든 기기에서 결과가 동일하지만, 새 운행 번호를 반영하려면 앱 자산 재생성과 배포가 필요하다.
* 발견한 매핑을 기기 DB에 영구 저장하면 재사용성은 높지만 테스트 단계에서 잘못된 매핑이 오래 남을 수 있다.
* 정적 JSON 위에 메모리 오버레이를 두면 앱 재시작 전까지 발견 결과를 재사용하면서 잘못된 데이터의 지속 범위를 제한할 수 있다.

## 3. 결정 및 이유

테스트 단계에서는 정적 JSON을 기본값으로 유지하고, 출발역과 목적지역 시간표에서 검증된 신규·교정 매핑만 메모리에 저장한다. 향후 Google Sheets와 Apps Script를 마스터 매핑 저장소로 사용할 예정이므로 저장 접근은 `TrainNumberMappingStore` 계약으로 유지했다.

`trainno` 후보는 부분 문자열로 찾지 않는다. 두 API 번호에서 숫자만 추출하고 선행 0을 제거한 값이 완전히 같은 경우만 후보로 인정한다. 서로 다른 후보가 여러 개이면 오매칭을 피하기 위해 `UNKNOWN`으로 남긴다.

제품 정책에 따라 출발·목적지 시간 순서는 비교하지 않는다. 동일 열차가 목적지역 시간표에 존재하면 정차로 판정하므로, 순환선이나 반복 운행에서는 이미 지난 역을 정차로 볼 가능성을 수용한다.

## 4. 구현 내용

* `TrainNumberMappingStore`에 `upsert`를 추가하고 `AssetTrainNumberMappingStore`에 스레드 안전한 프로세스 수명 메모리 오버레이를 구현했다. 메모리 값이 정적 자산보다 우선한다.
* `TrainStopRepository`를 열차별 호출에서 경로 단위 배치 판정으로 변경했다.
* 매핑된 번호가 목적지역에 없거나 매핑 자체가 없으면 목적지역 전체 시간표를 한 번 조회해 동일 숫자 본체 후보를 찾는다.
* 유일 후보는 출발역 시간표에서도 확인한 뒤 신규 저장하거나 오래된 매핑을 교정한다. 출발역 검증 실패, 복수 후보, API 실패는 저장하지 않는다.
* 목적지역 전체 시간표는 같은 노선·방향의 fallback 열차가 공유하며, `totalCount`가 1,000건을 넘으면 후속 페이지를 이어서 조회한다.
* 진단 모델에 기존 매핑, 발견 후보, 최종 번호, 갱신 여부를 추가하고 매핑 성공·발견·교정·후보 없음·후보 충돌·출발역 검증 실패 사유를 구분했다.

## 5. 검증 결과

* JVM 단위 테스트: 8개 스위트, 65개 테스트, 실패 0개, 오류 0개, 건너뜀 0개
* 추가 검증: 정적 매핑 우선, `0472 ↔ K472`, `0472 ≠ 1472`, 복수 후보 보류, 신규 매핑 저장, 기존 매핑 교정, 출발역 검증 실패 시 미저장, fallback 공유, 1,000건 초과 페이지, API 실패 격리, 취소 전파, 프로세스 재생성 시 메모리 초기화
* Android UI 테스트 Kotlin 컴파일: 성공
* Lint: 오류 0개, 기존 설정·의존성 업데이트 관련 경고 3개
* Debug APK 빌드: 성공
* `adb devices` 결과 연결된 기기가 없어 실제 기기 검증은 수행하지 못했다.

## 6. 남은 작업 / 보류 사항

* 실기기에서 대표 정차·미정차·매핑 교정 사례를 확인한다.
* 숫자 후보가 없을 때 `DOES_NOT_STOP`으로 표시하는 정책이 API 데이터 누락을 오판하지 않는지 실제 운행 표본으로 검증한다.
* Google Sheets·Apps Script 연동 시 서버 측 충돌 검사, 승인 절차, 인증과 실패 시 로컬 동작을 별도로 설계한다.
