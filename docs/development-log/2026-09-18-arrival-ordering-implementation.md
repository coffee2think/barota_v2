# 2026-09-18 — 예상 진입 순서 정렬 구현 (T04)

## 1. 배경 / 문제

사용자가 MVP 태스크 문서의 정렬 기능을 요청했다. 문서 전체를 일괄 구현하는 요청으로 해석하지 않고 T04를 수행했다. 기존 노선명 → 방향 → 예상 초 정렬은 예상 진입 순서를 우선하지 않았다. 특히 API의 운행 중 `barvlDt=0`을 실제 즉시 도착으로 취급하면 여러 역 전방 열차가 맨 앞에 표시된다.

## 2. 검토한 선택지

- 단순 초 오름차순 및 null 후순위: 운행 중 0초와 출발 완료를 구분하지 못해 제외했다.
- 전체 `ordkey` 또는 응답 `rowNum` 우선: 방향·종착역·운행유형이 포함된 키/응답 위치를 전체 열차의 시간 순서로 사용할 근거가 없어 제외했다.
- 상태로 시간을 정규화한 뒤 유효 초 우선, 순번은 동률 보조로 사용: 실제 응답과 공식 필드 정의에 맞아 채택했다.

## 3. 결정 및 이유

서울시 공식 [실시간 도착 API 필드 설명](https://data.seoul.go.kr/dataList/openApiView.do?infId=OA-12764&srvType=A)을 확인했다. `barvlDt`는 초 단위 도착 예정시간, `arvlCd`는 0 진입 / 1 도착 / 2 출발 / 3 전역 출발 / 4 전역 진입 / 5 전역 도착 / 99 운행 중이다. `ordkey`는 방향 1자리, 순번 1자리, 역 차이 3자리, 종착역, 급행 여부 1자리로 구성된다. `rowNum`은 도착 순서로 사용하지 않는다.

같은 날 실시간 API를 독산과 시청에 읽기 전용 요청했다. 키와 키 포함 URL은 출력하거나 기록하지 않았다. 독산의 7개 행은 모두 `barvlDt=0`, `arvlCd=99`였고 메시지는 2~12개 역 전방 등을 나타냈다. 시청의 13개 혼합 노선/방향 응답에는 `barvlDt=0, arvlCd=1`(현재 역 도착), 양수 90/150/200/240/270/390초, 운행 중 0초가 함께 존재했다. 따라서 0초만으로 즉시 도착을 추론하지 않는다. 독산의 서로 다른 행선지/급행 여부에서 순번 1이 반복돼 순번만으로도 실제 전체 순서를 보장할 수 없다.

정책은 다음과 같다.

1. 현재 역 출발 완료(`arvlCd=2`)를 제외한다. 전역 출발(`3`)은 제외하지 않는다.
2. 양수 초는 유효 예상시간이다. 0초는 진입/도착 상태에서만 유효하다.
3. 그 외 0초, 음수, 누락, 정수 파싱 실패/범위 초과는 각각 이유를 보존하고 시간은 null로 정규화한다.
4. 유효 초 오름차순 → 미확인 후순위. 동률은 형식 검증된 순번 → 열차번호 → ID다. 노선/방향이나 역 차이로 시간 추정하지 않는다.

미확인 버킷의 정렬은 안정적인 표시 규칙일 뿐 실제 진입 순서를 보장하지 않는다. 예상 초는 API 수신 스냅샷 기준이며 경과시간 차감/실시간 카운트다운은 구현하지 않았다.

## 4. 구현 내용

- `ArrivalOrdering.kt`: 순수 시간 정규화와 공통 정렬, 유효 0초 및 Int.MAX_VALUE 경계 처리.
- `RealtimeArrivalDto`/`TrainArrival`: 원본 순서 키, 상태, 시간 확인 유형 전달.
- `SeoulArrivalRepository`: 기존 방향 필터 후 정렬/출발 제외 → 정차 조회 순서. 비동기 정차 조회 후에도 정렬된 목록 순서를 유지한다.
- `ArrivalScreen`: 미확인 시간 및 순서 보장 불가 안내. 별도 최소시간 계산 대신 최종 목록의 첫 항목을 배경 기준으로 사용한다. T06의 기존 디버그 덮어쓰기는 이번에 변경하지 않았다.
- 순수 정책 테스트 6개와 Repository 통합 테스트 1개 추가. 기존 실제 독산 fixture에 운행 중 0초가 즉시 도착이 되지 않는 회귀 검증 추가. 기존 화면 테스트는 첫 최종 목록 항목 기준으로 수정했다.

## 5. 검증 결과

다음 명령이 성공했다.

```powershell
./gradlew.bat --no-daemon --offline --gradle-user-home .gradle-user '-Pkotlin.compiler.execution.strategy=in-process' testDebugUnitTest compileDebugAndroidTestKotlin lintDebug assembleDebug
```

- 단위 테스트 46개, 실패 0개. 뒤섞인 입력, 같은 시간, 다른 노선, 순번/번호/ID 동률, 유효/미확인 0초, 음수, 누락, 파싱 실패, 최대 정수 및 출발 완료 제외를 검증했다.
- Repository 통합 테스트: 방향 필터 → 시간 정렬 → 개별 정차 상태 전달; 제외 열차에는 정차 요청 없음.
- Compose 테스트 코드 컴파일 성공. 기기에서 실행한 결과가 아니며 실제 색상/배치를 검증한 것으로 기록하지 않는다.
- Lint: 오류 0, 기존 경고 2개(`OldTargetApi`, `NewerVersionAvailable`). 빌드 환경의 analytics 디렉터리 및 복사 SDK의 platform-tools 부재 경고도 있었으나 빌드는 성공했다.
- APK: `app/build/outputs/apk/debug/app-debug.apk` (20,219,848 bytes).

기존 SDK 경로의 Java ZIP 접근 권한 문제를 피하기 위해 앞선 방향 작업에서 마련한 동일 플랫폼/빌드 도구 복사본을 검증에만 사용했다. `local.properties`의 sdk.dir를 잠시 복사 SDK로 전환한 뒤 원래 경로로 복원했다. API 키는 변경하지 않았다. 원래 SDK 경로의 환경 문제가 해결됐다고 주장하지 않는다.

## 6. 남은 작업 / 보류 사항

- 연결 기기/에뮬레이터 Compose 테스트, 실제 운행 중 순서/배경과 스마트폰 인수 검증은 미실행.
- 실제 출발 완료 응답은 이번 조회에서 확보하지 못해 해당 경계는 공식 코드 정의와 합성 테스트로 검증했다. 이전 실제 독산 fixture를 보존했으며 이번 실시간 조회 전체를 새 fixture로 저장하지 않았다.
- 미확인 항목의 실제 전체 순서, API 중복 행 제거, 수신시간 지연 보정은 보장하지 않는다.
- T05 시간표 정차 판정 보강, T06 디버그 상태 격리/전체 색상 개선은 별도 작업이다. 기존 방향 지원 범위도 확장하지 않았다.
