# 기능 단위 작업 브랜치 운영 지침 추가

## 1. 배경 / 문제

기능 작업을 `main` 브랜치에서 직접 진행하면 진행 중인 변경과 완료된 변경의 경계가 불명확해지고, 기능별 검토나 병합 및 되돌리기가 어려워질 수 있다. 기능 단위로 변경을 격리하는 공통 작업 원칙이 필요했다.

## 2. 검토한 선택지

* `main`에서 직접 작업하고 커밋만 기능별로 나누는 방식은 브랜치 전환이 없지만 작업 도중 변경을 격리할 수 없다.
* 기능 단위마다 별도 브랜치를 만들면 브랜치 수는 늘어나지만 구현, 검증, 커밋과 후속 병합의 범위를 명확히 유지할 수 있다.
* 에이전트 이름을 브랜치 접두사로 사용하면 작업 주체를 바로 알 수 있지만, GitHub에 이미 남는 작성 도구 정보와 중복되고 브랜치명이 구현 목적보다 작업 도구를 강조하게 된다.

## 3. 결정 및 이유

새로운 기능, 버그 수정, 리팩토링과 의미 있는 UX 변경은 `main`을 기준으로 `<작업유형>/<작업명>` 브랜치를 생성한 뒤 진행한다. 작업 유형은 `feature`, `fix`, `refactor`, `docs`, `chore`로 구분하고 브랜치명에는 에이전트 이름을 넣지 않는다. 기능별 변경을 독립적으로 검토하고 병합하면서 브랜치명이 구현 목적을 나타내도록 하기 위해서다.

## 4. 구현 내용

* 루트 `AGENTS.md`에 작업 브랜치 운영 지침을 추가했다.
* 파일 수정 전에 작업 브랜치를 생성하거나 전환하도록 명시했다.
* 구현, 검증과 커밋을 작업 브랜치에서 수행하고 `main`에 직접 커밋하지 않도록 했다.
* 브랜치명을 작업 유형과 kebab-case 작업명으로 구성하고 에이전트 이름은 제외하도록 했다.
* 작업과 무관한 기존 변경을 스테이징하거나 커밋하지 않도록 했다.

## 5. 검증 결과

* 이 지침 변경은 `main`에서 분기한 `docs/work-branch-policy` 브랜치에서 수행했다.
* 문서 변경만 포함하므로 애플리케이션 테스트와 빌드는 수행하지 않았다.

## 6. 남은 작업 / 보류 사항

* 이후 기능 단위 작업에서 지침을 지속적으로 적용한다.
