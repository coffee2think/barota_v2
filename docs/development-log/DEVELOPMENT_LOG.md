# 지하철 바로타 개발 기록

이 문서는 의사결정의 배경과 실제 구현·검증 결과를 시간순으로 누적한다. 앞으로 기능을 변경할 때마다 선택한 안, 검토한 대안, 변경 파일, 테스트 결과와 남은 과제를 함께 기록한다.

## 2026-09-15 — 프로젝트 방향 및 기반 기술 결정

### 배경

- 빠른 개발과 안정성이 가장 중요하다.
- 테스트 가능한 기기는 Galaxy S23(Android 16)이며 iPhone 확장은 고려하지 않는다.
- 개발자는 Java, Spring, Spring Boot 경험이 있는 백엔드 신입 개발자다.
- 개인 기기와 포트폴리오 시연용 APK가 우선이지만 Play 스토어 운영 가능성도 고려한다.

### 결정

- Android 네이티브, Kotlin, Jetpack Compose를 선택했다.
- MVVM, ViewModel + StateFlow, Hilt로 화면 상태와 의존성을 관리한다.
- Retrofit + OkHttp, kotlinx.serialization로 서울시 API를 연결한다.
- Material 3, Navigation Compose, minSdk 26을 사용한다.
- 앱 이름은 `지하철 바로타`, 애플리케이션 ID는 `com.gilbit.barota`, 개발자 이름은 `길빛 스튜디오(Gilbit Studio)`로 정했다.
- 초기 역 선택 화면은 앱에 포함한 JSON과 검색 가능한 바텀시트를 사용하는 표준형으로 구현했다.
- 테스트는 ViewModel 단위 테스트, Compose UI 테스트, Fake Repository를 조합한 핵심 균형형으로 정했다.

### 검토한 대안

- Flutter와 React Native: Android만 대상으로 하므로 플랫폼 계층과 새 언어·프레임워크 학습 비용이 불필요하다고 판단했다.
- MVI 또는 Compose 로컬 상태만 사용: 초기 규모에는 각각 구조가 과하거나 확장 시 상태 관리가 어려워 MVVM을 선택했다.
- Ktor Client와 HttpURLConnection: 현재 경험과 Android 적용 사례를 고려해 Retrofit을 선택했다.
- Moshi와 Gson: Kotlin 친화성과 컴파일 타임 변환을 고려해 kotlinx.serialization을 선택했다.
- 수동 DI와 Koin: Android 통합 및 컴파일 시 검증을 위해 Hilt를 선택했다.

### 구현 및 검증

- 대표 역 61개의 선택, 검색, 맞바꾸기, 동일 역 방지, 화면 이동을 구현했다.
- ViewModel 단위 테스트 4개, Compose UI 테스트 컴파일, Lint, Debug APK 빌드에 성공했다.
- API 35 에뮬레이터에서 강남 → 가산디지털단지 선택 흐름을 수동 검증했다.

관련 세부 내용은 `TECH_DECISION_REPORT.md`에 정리되어 있다.

## 2026-09-16 — 실시간 도착정보 화면 1차 구현

### 요구사항과 선택

- 출발역과 도착역을 고른 뒤 다음 화면에서 들어오는 열차 정보를 보여준다.
- 세 가지 범위를 검토했다.
  1. 출발역으로 들어오는 모든 열차를 보여주는 전광판형
  2. 출발역과 도착역이 공유하는 직통 노선만 필터링하는 방식
  3. 환승 경로를 계산해 첫 승차 열차만 보여주는 방식
- 빠진 역과 노선 연결 데이터는 나중에 보완하기로 했으므로, 데이터 완성도와 무관하게 동작하는 1번 전광판형을 선택했다.
- 사용자가 보유한 `서울시 지하철 실시간 도착정보(일괄)` API 키를 로컬 설정에서 주입해 서울시 실시간 도착 데이터 계열을 호출하는 방향으로 정했다.

### 구현

- 임시 선택 결과 화면을 실시간 도착정보 화면으로 교체했다.
- 출발·도착역 요약, 노선, 방향, 도착 메시지, 현재 위치, 종착역, 급행·막차 표시를 추가했다.
- 초기 조회, 로딩, 빈 결과, 네트워크·API 오류, 수동 새로고침 상태를 구현했다.
- Retrofit API, 응답 DTO, 도메인 모델, Repository와 Hilt 바인딩을 추가했다.
- API 키는 `local.properties`의 `SEOUL_SUBWAY_API_KEY`로 주입하고 버전 관리에서 제외한다.
- 서울시 지하철 API가 HTTP로 제공되므로 Android Network Security Config에서 `swopenapi.seoul.go.kr` 호스트에만 평문 통신을 허용했다.
- API 응답의 알려지지 않은 필드는 무시해 필드 추가에 대한 내성을 유지했다.
- 정상 응답의 `errorMessage` 포맷과 오류 응답의 최상위 `code/message` 포맷을 모두 처리한다.

### API 사용 범위

- 현재 화면은 출발역 하나의 데이터만 필요하므로 `realtimeStationArrival`의 역명 조회 경로를 사용한다.
- 한 번에 최대 100건을 요청하고 선택한 출발역과 역명이 정확히 일치하는 결과만 표시한다.
- 인증키 값은 아직 프로젝트에 입력하지 않았으므로 실제 응답 검증은 키 설정 후 진행해야 한다.
- 공개 배포 전에는 APK에서 인증키를 추출할 수 있다는 한계 때문에 Spring Boot 프록시로 이전한다.

### 새로고침 결정 보류

- 첫 버전은 화면 진입 시 한 번 조회하고 사용자가 직접 새로고침한다.
- 자동 갱신은 호출량과 UX에 영향을 주므로 실제 API 확인 후 갱신 주기를 별도로 선택한다.

### 남은 작업

- 사용자의 로컬 API 키 설정 후 실제 기기에서 성공·오류 응답을 검증한다.
- API 응답 명세와 실제 데이터의 차이가 있으면 DTO와 메시지 변환을 조정한다.
- 자동 갱신 여부와 주기를 결정한다.
- 전체 역 및 노선 연결 데이터를 확보한 뒤 목적지 방향·환승 경로 필터링으로 확장한다.

### 검증 결과

- 서울시 샘플 키로 서울역을 조회해 정상 응답 구조와 실제 필드값을 확인했다.
- 새 ViewModel 단위 테스트 3개를 포함한 전체 단위 테스트가 통과했다.
- Android UI 테스트 코드 컴파일, Lint, Debug APK 빌드가 성공했다.
- Lint 결과는 오류 0개다. targetSdk 36과 사용 중인 OkHttp 버전에 관한 정보성 업데이트 경고 2개가 남아 있다.
- 실제 사용자 키를 사용한 호출과 Galaxy S23 화면 확인은 아직 진행하지 않았다.

## 2026-09-16 — 열차별 정차역 확인 방법 조사

### 질문

- 실시간 도착정보에 나타난 열차가 앞으로 어떤 역에 정차하는지 확인할 수 있는가?
- 별도로 발급받은 `서울시 지하철 실시간 열차 위치정보` API 키를 사용해야 하는가?

### 조사 결과

- 현재 사용하는 실시간 도착정보는 열차번호(`btrainNo`), 노선, 상·하행, 종착역(`bstatnNm`), 일반·급행 구분과 현재 위치 메시지를 제공한다.
- 실시간 열차 위치정보는 열차번호(`trainNo`), 현재 역, 상·하행, 종착역, 진입·도착·출발 상태, 급행·막차 여부를 제공한다.
- 두 API 모두 한 열차가 앞으로 정차할 역들의 순서나 목록은 제공하지 않는다.
- 따라서 실시간 열차 위치정보를 추가 호출해도 선택한 목적지에 해당 열차가 정차하는지는 직접 판별할 수 없다.

### 결정 및 권장 방향

- 현재의 도착정보 목록 기능에는 실시간 열차 위치정보 API를 추가하지 않는다. 도착정보 API가 이미 현재 위치 메시지와 열차번호를 제공하므로 정보가 상당 부분 중복되고 호출량만 늘어난다.
- 정차역 목록은 `서울교통공사_역코드로 지하철 열차 시간표 검색` 또는 최신 열차시간표 데이터와 실시간 도착정보의 열차번호를 결합해 계산하는 방식을 우선 검토한다.
- 일반열차는 노선 순서 데이터만으로 대략 표시할 수 있지만, 급행·특급·지선·서로 다른 종착역을 정확히 처리하려면 열차번호별 시간표 매칭이 필요하다.
- 실시간 열차 위치정보 API는 향후 노선도 위에서 열차의 현재 위치를 움직여 보여주거나, 해당 열차가 어느 역을 통과 중인지 상세 추적할 때 도입한다.

### 참고한 공식 데이터

- 서울시 지하철 실시간 도착정보: https://data.seoul.go.kr/dataList/OA-12764/A/1/datasetView.do
- 서울시 지하철 실시간 열차 위치정보: https://data.seoul.go.kr/dataList/OA-12601/A/1/datasetView.do
- 서울교통공사_역코드로 지하철 열차 시간표 검색: https://data.seoul.go.kr/dataList/OA-101/S/1/datasetView.do
- 서울시 교통공사 지하철역 열차시간표 현황: https://data.seoul.go.kr/dataList/OA-22750/A/1/datasetView.do

## 2026-09-16 — 목적지 정차 여부 UX 프로토타입

### 요구사항과 결정

- 열차시간표 API를 연결하기 전에 `목적지 정차`와 `목적지 미정차` 판단 결과를 크게 보여주는 UX를 먼저 검증한다.
- 정차하는 열차는 초록 배경과 웃는 이모티콘으로 표현한다.
- 미정차 열차의 배경은 빨강과 노랑 중 확정하지 않았으므로 두 안을 모두 구현해 실제 Galaxy S23에서 비교한 뒤 선택한다.
- 실제 서비스 화면에 테스트 조작이 남지 않도록 테스트 버튼은 `BuildConfig.DEBUG`인 디버그 APK에만 표시한다.

### 구현

- 실시간 도착정보 화면 상단에 `정차함`, `미정차·노랑`, `미정차·빨강` 테스트 버튼을 추가했다.
- 각 버튼을 누르면 배경색, 이모티콘, 선택한 목적지역 이름과 안내 문구가 포함된 전체 화면 결과를 표시한다.
- 닫기 아이콘과 `다른 결과 보기` 버튼으로 도착정보 화면으로 돌아가 다른 안을 바로 비교할 수 있다.
- 정차 여부 계산이나 열차시간표 API 호출은 이번 단계에 포함하지 않았다.

### 검증

- 세 테스트 버튼이 각각 초록·노랑·빨강 결과 화면을 여는 Compose UI 테스트를 추가했다.
- 전체 ViewModel 단위 테스트 통과, Compose UI 테스트 코드 컴파일 성공, Lint 오류 0개, Debug APK 빌드 성공을 확인했다.

### 다음 결정

- Galaxy S23에서 두 미정차 화면을 비교한 뒤 노랑 또는 빨강 배경을 최종 선택한다.
- 선택이 끝나면 `서울시 교통공사 지하철역 열차시간표 현황` API를 연결하고 실제 판정 결과를 이 화면에 전달한다.

## 2026-09-16 — 정차 여부를 도착정보 카드에 직접 표시

### 피드백과 결정

- 미정차 결과는 노란색보다 빨간색 배경을 사용하기로 확정했다.
- 정차 여부를 별도 전체 화면에서 확인하면 열차 목록과 판단 결과를 오가야 하므로, 실시간 도착정보 목록에서 각 열차를 보는 즉시 판단할 수 있도록 변경한다.
- 여러 열차가 서로 다른 정차 결과를 가질 수 있으므로 화면 전체가 아닌 개별 열차 카드 단위로 상태를 표시한다.
- 색각이나 점멸을 인지하기 어려운 경우에도 의미가 전달되도록 색상 외에 이모티콘과 행동 문구를 함께 사용한다.

### 구현

- 열차 도메인 모델에 `UNKNOWN`, `STOPS`, `DOES_NOT_STOP` 목적지 정차 상태를 추가했다.
- `STOPS` 카드는 고정 초록 배경과 `😊 목적지 정차 · 타도 돼요` 문구를 표시한다.
- `DOES_NOT_STOP` 카드는 두 단계의 빨간색을 700ms 간격으로 부드럽게 왕복하는 점멸과 `😠 목적지 미정차 · 타면 안 돼요` 문구를 표시한다.
- 기존 전체 화면 테스트 결과 UI와 노란색 안은 제거했다.
- 디버그 도착정보 화면에서 `정차·초록`, `미정차·빨강 점멸`, `판정 표시 해제` 버튼으로 실제 열차 카드들의 상태를 즉시 전환할 수 있다.
- 이후 시간표 API 판정 결과는 열차별 정차 상태에 연결하면 같은 UI를 그대로 사용한다.

### 검증

- 테스트 상태 변경 후 카드가 초록, 빨강 점멸, 기본 상태로 바뀌는 Compose UI 테스트를 수정했다.
- 전체 단위 테스트 통과, Compose UI 테스트 코드 컴파일 성공, Lint 오류 0개, Debug APK 빌드 성공을 확인했다.

## 2026-09-16 — 운행 종료 시간에도 확인 가능한 테스트 카드

### 발견한 문제

- 기존 테스트 버튼은 API에서 받은 실제 열차 카드에만 상태를 덮어썼다.
- 새벽처럼 운행 중인 열차가 없어 도착정보가 비어 있으면 변경할 카드가 없으므로 버튼을 눌러도 시각적 변화가 없었다.

### 수정

- 디버그 도착정보 화면에 API 결과와 무관하게 항상 나타나는 `테스트용 열차 카드`를 추가했다.
- 테스트 카드는 2호선 내선, 성수행, 3분 20초 후, 역삼 출발이라는 고정 예시 데이터를 사용한다.
- 기존 테스트 버튼으로 테스트 카드와 실제 열차 카드의 상태를 동시에 초록 정차, 빨강 점멸 미정차, 미판정으로 전환한다.
- 릴리스 빌드에서는 테스트 버튼과 테스트 카드가 모두 제외된다.

### 검증

## 2026-09-16 — 가장 가까운 열차와 결과 화면 배경 동기화

### 요구사항과 결정

- 개별 열차 카드뿐 아니라 실시간 도착정보 화면의 가장 바탕이 되는 배경도 즉시 알아볼 수 있게 한다.
- `barvlDt`에서 변환한 `arrivalSeconds`가 가장 작은 열차를 가장 진입이 가까운 열차로 판단한다.
- 도착 예정 시간이 없는 항목은 가장 뒤로 취급한다.
- 열차가 없거나 가장 가까운 열차의 목적지 정차 여부가 아직 `UNKNOWN`이면 기존 기본 배경을 유지한다.

### 구현

- 가장 가까운 열차가 목적지에 정차하면 화면 본문과 상단 앱 바 배경을 초록색으로 표시한다.
- 가장 가까운 열차가 미정차하면 화면 본문, 상단 앱 바와 해당 열차 카드가 동일한 빨간색 점멸 값을 공유한다.
- 화면과 카드가 각각 애니메이션을 실행해 점멸 시점이 어긋나지 않도록, 화면에서 하나의 애니메이션 색상을 만든 뒤 카드에 전달한다.
- 디버그 테스트 상태는 실제 판정보다 우선하므로 새벽의 테스트용 카드에서도 전체 배경 동기화를 확인할 수 있다.

### 검증

- 테스트 버튼으로 초록·빨강 점멸·기본 상태를 전환할 때 화면과 카드 상태가 함께 바뀌는 UI 테스트 조건을 추가했다.
- 서로 다른 도착 예정 시간을 가진 열차 중 가장 가까운 열차의 상태가 화면 배경에 적용되는 테스트를 추가했다.
- 전체 단위 테스트 통과, Compose UI 테스트 코드 컴파일 성공, Lint 오류 0개, Debug APK 빌드 성공을 확인했다.

## 2026-09-16 — 열차시간표 API 기반 목적지 정차 판정

### 1. 배경 / 문제

- 실시간 도착정보에 포함된 열차가 사용자가 고른 목적지역에 앞으로 정차하는지를 실제 데이터로 판정해야 한다.
- 실시간 도착정보만으로는 전체 정차역을 알 수 없으므로 사용자가 발급받은 `서울시 교통공사 지하철역 열차시간표 현황` API를 결합한다.
- 목적지역 시간표에 열차번호가 없다는 사실만으로 미정차를 확정하면 API 범위 차이, 열차번호 체계 불일치 또는 오류를 위험한 빨간색 안내로 오판할 수 있다.

### 2. 검토한 선택지

- 목적지역 시간표에서 열차번호 존재 여부만 확인: 구현은 단순하지만 이미 지나온 역도 정차로 판단하고, 열차번호 매칭 실패도 미정차로 오판할 수 있다.
- 출발역과 목적지역의 같은 열차번호 및 시각을 함께 확인: 호출은 늘어나지만 현재 열차가 시간표에 존재하는지와 목적지역이 앞으로 남아 있는지를 함께 검증할 수 있다.
- 노선도와 급행 정차역을 앱에 정적으로 저장: 호출은 줄지만 시간표 변경, 지선, 임시 운행을 앱 업데이트 없이 반영하기 어렵다.

### 3. 결정 및 이유

- 실시간 도착정보의 열차번호(`btrainNo`)를 시간표 API의 열차번호(`trainno`)와 정확히 매칭한다.
- 목적지역과 출발역 양쪽의 시간표 행을 확인하고, 목적지역 시각이 출발역 시각보다 뒤일 때만 `STOPS`로 판정한다.
- 목적지역 행은 없지만 출발역 행이 확인되면 `DOES_NOT_STOP`으로 판정한다.
- 출발역에서도 같은 열차를 확인하지 못하거나 시간 값이 해석되지 않으면 안전하게 `UNKNOWN`을 유지한다. 확인 실패를 미정차로 표시하지 않는 것이 잘못된 탑승 금지 안내보다 안전하기 때문이다.
- 종착역과 목적지역이 같으면 별도 시간표 호출 없이 `STOPS`로 판정한다.

### 4. 구현 내용

- `getTrainSch` 응답 DTO, Retrofit API와 `TrainStopRepository`를 추가하고 Hilt로 연결했다.
- 시간표 키는 `local.properties`의 `SEOUL_TIMETABLE_API_KEY`에서 BuildConfig로 주입한다. 키 값은 저장소에 기록하지 않는다.
- 현재 날짜를 서울 시간대로 계산해 평일 또는 주말 시간표와 일반 시간표(`tmprTmtblYn=N`)를 조회한다.
- 공식 제공 범위에 맞춰 우선 1~9호선만 판정하며 그 외 노선은 `UNKNOWN`으로 둔다.
- 출발역·목적지역 시간의 선후관계를 비교해 이미 지나온 목적지역을 정차 가능으로 오판하지 않게 했다. 24시 이후 표기도 비교할 수 있도록 시간 문자열을 영업일 기준 초 단위로 변환한다.
- 열차별 조회는 동시에 최대 4개만 실행해 순간적인 API 요청 집중을 제한한다.
- 개별 시간표 요청 실패는 해당 열차만 `UNKNOWN`으로 처리해 실시간 도착정보 목록 자체는 계속 표시한다.
- 출발역뿐 아니라 목적지역도 ViewModel과 Repository 요청 경로에 전달하며, 출발역 또는 목적지역이 바뀌면 새로 조회한다.
- 시간표 API 호스트가 HTTP를 사용하므로 `openapi.seoul.go.kr`에만 평문 통신을 허용했다.

### 5. 검증 결과

- 목적지역 정차, 목적지역 미정차, 이미 지나온 목적지역, 열차번호 확인 불가, 미지원 노선, 목적지역과 종착역 일치에 대한 단위 테스트를 추가했다.
- 전체 단위 테스트, Android UI 테스트 코드 컴파일, Lint와 Debug APK 빌드가 성공했다.
- Lint 오류는 0개이며 기존의 targetSdk 및 OkHttp 업데이트 안내 경고 2개만 남아 있다.
- 실제 `SEOUL_TIMETABLE_API_KEY`는 이 작업 환경의 `local.properties`에 입력되지 않아 사용자 키를 이용한 실시간 시간표 매칭과 Galaxy S23 실제 화면은 아직 검증하지 않았다.

### 6. 남은 작업 / 보류 사항

- `local.properties`에 시간표 API 키를 설정한 뒤 실제 운행 시간에 1~9호선의 일반·급행·순환선 사례를 Galaxy S23에서 확인한다.
- 공휴일이 주말 시간표와 동일한지, 임시 시간표(`tmprTmtblYn=Y`)를 언제 우선해야 하는지 실제 응답으로 검증한다.
- 1~9호선 외 운영기관 노선은 이 API의 제공 범위와 열차번호 호환성을 확인한 뒤 확장한다.
- 현재 방식은 표시 열차마다 최대 2회 시간표 요청이 필요하다. 실제 운영 전 Spring Boot 프록시에서 캐시, 호출 제한과 키 보호를 적용한다.
- 시간표는 계획 정보이므로 운행 변경 상황에서는 실제 정차와 차이가 날 수 있다는 사용자 안내를 추후 검토한다.
