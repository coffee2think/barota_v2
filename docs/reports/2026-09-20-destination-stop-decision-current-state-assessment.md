# 목적지 정차 판정 로직 현황 평가 및 개선 권고

- 작성일: 2026-09-20
- 평가 대상: 선택 가능한 전체 역 목록이 적용된 현재 앱의 목적지 정차 판정 경로
- 방법: 구현 코드·자동 테스트·기존 실제 API 진단 기록의 정적 검토
- 이 문서는 개선 권고이며, 앱 동작을 변경하지 않는다.

## 결론

현재 로직은 **제한된 1호선 종로3가–독산 구간에서만 조건부로 동작하도록 만든 MVP 구현**이다. 시간표 API 응답이 정상적으로 같은 열차번호를 반환한다는 전제에서는 출발역과 목적지역의 시간 순서를 비교하는 핵심 알고리즘이 타당하다.

그러나 전체 655개 역이 선택 가능한 현재 상태에서 “어느 출발역·목적지 조합에서도 열차가 정차하는지 판별한다”는 기능으로는 정상 동작하지 않는다. 이유는 다음 두 층위가 모두 제한돼 있기 때문이다.

1. 방향 판정기가 1호선 14개 역 이외의 경로를 조회 전에 차단한다.
2. 현재 시간표 요청의 `searchDt`가 실제 2호선 시간표 결과까지 0건으로 만드는 것이 확인됐고, 독산 1호선은 `searchDt` 유무와 관계없이 실시간 열차번호와 시간표 번호가 매칭되지 않았다.

따라서 현재 UI에서 초록/빨강 상태가 보이는 경우는 종착역 일치 같은 빠른 판정 또는 특정 시간표 호환 구간에 한정된다. 대부분의 경우 `UNKNOWN`은 안전한 실패 처리이지만, 사용자는 이를 “판정 불가”로 받아들이게 된다.

## 평가 범위와 판정 기준

| 관점 | 평가 기준 | 현재 결과 |
| --- | --- | --- |
| 경로 진입 | 선택한 출발역·목적지에 대해 실시간 열차를 조회할 수 있는가 | 대부분 불가 |
| 후보 열차 선택 | 반대 방향·다른 노선 열차를 제외하되, 같은 방향의 단거리 열차는 유지하는가 | 지원 구간에서는 적절 |
| 정차 판정 | 목적지가 앞으로 남은 시간표 정차인지 판단하는가 | 시간표가 호환될 때만 적절 |
| 실패 안전성 | 데이터 부족을 미정차로 오판하지 않는가 | 일부 위험 존재 |
| 운영 검증 | 실제 API와 실제 기기에서 반복 검증됐는가 | 부족 |

## 현재 처리 구조

```text
전체 역 목록에서 출발역/목적지 선택
  → RouteDirectionResolver가 공통 노선과 방향을 확정해야 함
  → 확정된 경우에만 실시간 도착정보 호출
  → 노선 ID + API 방향으로 후보 열차 필터링
  → 열차별 시간표 API: 출발역과 목적지역의 같은 열차번호 조회
  → 목적지 시각 > 출발역 시각이면 STOPS
     목적지 행이 없거나 이미 지났으면 DOES_NOT_STOP
     확인 불가면 UNKNOWN
```

`RouteDirectionResolver`가 `Resolved`를 반환하지 않으면 [`ArrivalViewModel`](../../app/src/main/java/com/gilbit/barota/ui/arrival/ArrivalViewModel.kt)은 Repository 조회를 시작하지 않는다. 화면도 이 상태에서 열차 없음 메시지 대신 미지원/확인 불가 안내만 표시한다.

## 확인된 판단

### 1. 전체 역 데이터 갱신은 방향 판정 데이터를 제공하지 않는다 — 차단 요인

[`stations.json`](../../app/src/main/assets/stations.json)은 655개 역의 `id`, `name`, `lines`만 보존한다. [`Station`](../../app/src/main/java/com/gilbit/barota/data/model/Station.kt)의 모델에도 노선별 순서, 인접 역, 분기, 순환 방향, 서울시 API 노선 ID가 없다. `AssetStationRepository`는 이 목록을 이름순으로 정렬한다.

반면 [`RouteDirectionResolver`](../../app/src/main/java/com/gilbit/barota/domain/RouteDirectionResolver.kt)은 코드 내부의 `LINE_ONE_DOWN_STATIONS` 14개 역 인덱스 비교로 상행/하행을 정하고, `subwayId`도 `1001`로 고정한다. 1호선 이외 노선과 이 14개 역 밖의 1호선 경로는 `Unsupported`가 된다.

이는 테스트 전용 제한이 아니다. 운영 화면의 실시간 조회 전제조건이다. 전체 역 선택 UI와 전체 경로 지원 범위가 불일치한다.

### 2. 시간 순서 비교 알고리즘은 제한된 전제에서는 타당하다 — 조건부 정상

[`SeoulTrainStopRepository`](../../app/src/main/java/com/gilbit/barota/data/repository/SeoulTrainStopRepository.kt)은 같은 `trainno`와 역명을 출발역·목적지역 양쪽에서 찾는다. 출발역의 출발 시각(없으면 도착 시각)보다 목적지역의 도착 시각(없으면 출발 시각)이 큰 행 조합이 있으면 `STOPS`로 판단한다.

이 방식은 다음 오류를 피한다.

- 시간표에 목적지역이 있더라도 이미 지나간 역을 정차 예정으로 표시하는 오류
- 출발역 시간표에서 같은 열차를 찾지 못한 상태를 곧바로 미정차로 표시하는 오류
- 종착역과 목적지가 같은 명확한 경우에 불필요한 API 호출을 하는 문제

단위 테스트는 이후 정차, 목적지 미존재, 이미 지난 목적지, 미지원 노선, 종착역 일치를 검증한다. 다만 테스트의 시간표 응답은 모두 합성 데이터다.

### 3. 현재 `searchDt` 요청은 실시간 정차 판정을 사실상 무력화할 수 있다 — 높은 우선순위 결함

[`SeoulTrainStopRepository`](../../app/src/main/java/com/gilbit/barota/data/repository/SeoulTrainStopRepository.kt)은 모든 시간표 요청에 현재 서울 시각을 `searchDt`로 넣는다. 기존 실제 API 진단에서는 2026-09-19에 강남 2호선의 같은 열차가 `searchDt` 없이 출발역에서 1건, 목적지역에서 3건 조회됐지만 `searchDt`를 넣으면 각각 0건이 됐다.

코드는 아직 이 값을 항상 전송한다. 따라서 출발역 매칭 실패로 `UNKNOWN/ORIGIN_TRAIN_NOT_FOUND`가 발생할 수 있으며, 핵심 알고리즘이 실행될 데이터 자체가 사라진다. 이 사실은 [2026-09-19 진단 리포트](2026-09-19-arrival-card-color-diagnosis.md)의 실제 조회 기록으로 확인됐다.

### 4. 독산 1호선은 별도의 데이터 호환성 문제가 있다 — 높은 우선순위 제약

같은 실제 API 진단에서 독산 → 종로3가 상행 열차는 `searchDt` 포함 여부와 무관하게 출발역과 목적지역 시간표 모두 0건이었다. 즉 이 구간은 현재 실시간 `btrainNo`와 시간표 `trainno`의 체계 또는 제공 범위가 맞지 않는 것으로 보인다.

현재 알고리즘은 번호를 정확히 같게 비교하므로 이 경우 안전하게 `UNKNOWN`을 반환한다. 잘못된 빨강 안내를 줄인다는 점은 맞지만, 사용자가 원하는 정차 판별 결과는 제공하지 못한다.

### 5. 목적지역 0건을 곧바로 미정차로 확정하는 규칙은 위험하다 — 개선 필요

출발역에서 같은 열차를 찾고 목적지역에는 없으면 현재 코드는 `DOES_NOT_STOP`을 반환한다. 시간표 API의 응답 완전성과 대상 노선·운행 범위가 확인된 환경에서는 합리적이다.

하지만 위와 같이 공급자 필터나 데이터 범위가 결과를 0건으로 만들 수 있는 상황에서는 “행이 없음”이 실제 미정차를 뜻한다고 보장할 수 없다. 이 경우 빨간 “타면 안 돼요”는 안전하지 않은 안내다. 시간표 공급 계약이 검증되지 않은 경로에서는 `UNKNOWN`으로 유지해야 한다.

### 6. 현재 자동 테스트는 회귀 방지에는 유효하지만, 전체 역 지원이나 실제 API 호환성을 증명하지 않는다

- `RouteDirectionResolverTest`는 하드코딩한 동일 14개 역 목록의 182개 쌍을 검사한다. 전체 역 데이터에서 경로를 유도하는 테스트는 아니다.
- `SeoulTrainStopRepositoryTest`는 합성 응답으로 시간 비교 분기를 검증한다. 실제 API 응답의 `searchDt`·열차번호 호환성·공휴일·자정 경계는 검증하지 않는다.
- `SeoulArrivalRepositoryTest`는 실제 독산 실시간 fixture의 방향 필터를 확인하지만, 시간표의 실제 정차 결과 fixture는 없다.
- 기존 기록상 단위 테스트·UI 테스트 컴파일은 성공했지만, 연결 기기에서 UI 테스트와 실제 카드 검증은 수행되지 않았다.

## 정상 동작 여부

| 사용 상황 | 판정 | 근거 |
| --- | --- | --- |
| 1호선 종로3가–독산, 종착역=목적지 | 정상 동작 가능 | 시간표 없이 `TERMINAL_MATCH`로 즉시 `STOPS` |
| 1호선 종로3가–독산, 시간표가 정확한 동일 열차번호를 반환 | 조건부 정상 | 시간 순서 비교 로직과 단위 테스트 존재 |
| 1호선 종로3가–독산, 일반적인 실제 독산 열차 | 정상 판정 불가 | 실제 진단에서 양쪽 시간표 매칭 0건 |
| 2호선 등 다른 노선 | 현재 화면 경로에서는 동작하지 않음 | Resolver가 `Unsupported` 반환 후 조회를 중단 |
| 1호선의 지원 구간 밖 | 현재 화면 경로에서는 동작하지 않음 | 14개 역 목록 밖이면 `Unsupported` |
| 환승 경로·지선·순환선 | 현재 동작하지 않음 | 연결·분기·내외선 메타데이터가 없음 |

따라서 최종 평가는 **“제한된 데모/안전 실패 구현으로는 정상, 전체 역 기반의 목적지 정차 판별 기능으로는 미완성”**이다.

## 개선 권고

### P0 — 시간표 데이터 호환성부터 복구·검증

1. `searchDt`를 기본 요청에서 제거하고, 공급자 명세 및 실제 응답으로 유효한 날짜 조건이 확인된 경우에만 선택적으로 넣는다.
2. 강남 → 잠실처럼 실제로 매칭되는 경로의 응답을 식별 정보 없이 최소 fixture로 보관한다. `searchDt` 유무에 따른 행 소거와 출발·목적지 시각 비교를 계약 테스트로 고정한다.
3. 독산 등 시간표 데이터셋과 호환되지 않는 구간은 공급자 지원 범위와 연결 열차번호(`lnkgTrainno`) 사용 가능 여부를 확인한다. 근거가 확보되기 전에는 “정차 판정 지원 안 됨”으로 명시한다.

### P0 — 미정차 확정 규칙을 보수적으로 변경

목적지역 0건만으로 `DOES_NOT_STOP`을 반환하지 않는다. 다음 중 하나가 확인될 때만 빨간 상태를 허용한다.

- 해당 노선·날짜·방향·열차번호 조합에서 시간표 응답 완전성이 계약 테스트로 확인됨
- 신뢰 가능한 별도 운행 경로 데이터가 목적지역 미경유를 증명함

그 외에는 `UNKNOWN`과 구체적인 사유(예: `DESTINATION_SCHEDULE_UNVERIFIED`)를 반환한다. 이는 정보 부족을 탑승 금지 안내로 바꾸지 않는 안전 정책이다.

### P1 — 역 카탈로그와 별개로 데이터 기반 노선 그래프를 도입

`stations.json`은 선택·검색용으로 유지하고, 방향과 연결성은 별도 버전 관리 자산으로 분리한다. 예시는 다음과 같다.

```json
{
  "line": "1호선",
  "subwayId": "1001",
  "services": [
    {
      "id": "main",
      "directions": {
        "forward": "하행",
        "reverse": "상행"
      },
      "edges": [["종로3가", "종각"], ["종각", "시청"]]
    }
  ]
}
```

핵심은 역의 단일 순번이 아니라 **운행 서비스별 방향 있는 연결 구간**이다. 이 구조로 다음을 처리한다.

- 일반 직선 노선: 경로상의 두 역 순서로 상·하행 결정
- 2호선: 두 방향 후보를 내선·외선으로 모델링하고 사용자 또는 경로 규칙으로 선택
- 1호선·다른 지선: 공통 본선 이후 어느 분기로 가는지 별도 서비스/간선으로 표현
- 환승: 첫 탑승 노선만 판단하거나, 이후 단계에서 다구간 경로 탐색으로 확장

기존 하드코딩 배열은 이 자산으로 이관하고, Resolver는 자산을 읽어 경로와 API 노선 ID·방향을 반환하도록 바꾼다. 코드에 노선별 `if`를 추가하는 방식은 범위가 늘수록 검증과 유지보수가 어려워 권장하지 않는다.

### P1 — 정차 판정과 방향 필터를 독립적으로 검증

방향은 “어떤 실시간 열차를 후보로 보여 줄지”를 결정하고, 시간표는 “후보 열차가 목적지에 설지”를 결정한다. 두 판단의 데이터 출처와 실패 원인을 분리한다.

- 방향 그래프가 없으면 경로를 `Unsupported`으로 막되, 지원 범위를 역 선택 화면에서도 표시한다.
- 시간표가 호환되지 않으면 방향이 맞아도 카드 상태는 `UNKNOWN`으로 남기고 원인을 보여 준다.
- 실시간 방향값과 시간표 방향값은 각 API의 계약을 확인해 별도로 정규화한다. 한 API의 숫자 코드를 다른 API 문자열에 재사용하지 않는다.

### P2 — 관찰성·성능·운영 검증 강화

- 릴리스 화면에도 `정차 여부를 확인할 수 없어요` 같은 비위협적 안내를 제공하고, 디버그에는 현재처럼 사유와 매칭 건수를 유지한다.
- 동일 새로고침 안에서 열차별 시간표 요청은 최대 4개로 제한돼 있으나, 결과 캐시가 없다. 요청 키(노선·방향·역·열차번호·요일) 기준의 짧은 캐시와 취소 정책을 설계한다.
- 실제 API 응답을 비식별 fixture로 축적하고, 노선별 대표 정상/미정차/시간표 미지원 케이스를 계약 테스트로 운영한다.
- 지원 범위 확장마다 단위 테스트, 실제 API 대조, 실제 기기 확인을 완료 기준으로 기록한다.

## 권장 구현 순서

1. `searchDt` 제거 또는 조건화와 실제 호환 구간 계약 테스트를 먼저 수행한다.
2. 목적지역 0건의 빨간 판정을 보수적으로 `UNKNOWN`으로 바꾸고 사유를 추가한다.
3. 시간표가 호환되는 지원 구간을 명시적으로 결정한다. 독산 1호선은 별도 데이터 매핑 근거를 확보할 때까지 판정 지원 범위에서 제외한다.
4. 노선 그래프 자산·로더·Resolver를 구현하고, 기존 1호선 14개 역을 첫 데이터셋으로 이관한다.
5. 직선 노선부터 확대한 뒤, 2호선 순환과 분기 노선은 별도 서비스 모델 및 선택 UX를 추가한다.
6. 전체 역 선택 화면에 “선택 가능”과 “실시간 정차 판정 지원”을 구분해 표시한다.
