# 도착정보 카드 색상 미작동 진단 리포트

- 작성일: 2026-09-19
- 대상: Android 도착정보 화면의 정차·미정차 카드 및 화면 배경
- 진단 경로: 독산 → 종로3가(1호선 상행), 비교 경로: 강남 → 잠실(2호선 외선)
- 결론: 카드의 색상 렌더링 분기는 존재하지만, 실제 시간표 판정이 `UNKNOWN`으로 귀결되어 기본색이 표시된다.

## 1. 현상과 기대 동작

`ArrivalCard`와 화면 배경은 `DestinationStopStatus`에 따라 다음처럼 동작하도록 구현되어 있다.

| 상태 | 카드 | 화면 배경 | 문구 |
| --- | --- | --- | --- |
| `STOPS` | 고정 초록 `#DDF6E8` | 고정 초록 | 목적지 정차 |
| `DOES_NOT_STOP` | 두 빨강 사이를 700ms로 왕복 | 같은 빨강 애니메이션 | 목적지 미정차 |
| `UNKNOWN` | 테마 기본 컨테이너색 | 테마 기본 배경색 | 별도 판정 문구 없음 |

따라서 실제 카드가 기본색으로만 보이는 직접 원인은 색상 적용 실패가 아니라 `destinationStopStatus == UNKNOWN`이다. `CardDefaults.cardColors`에는 상태별 `containerColor`가 정상 전달된다.

## 2. 코드상 데이터 흐름

1. `SeoulArrivalRepository`가 실시간 도착정보를 노선·방향으로 필터링한다.
2. 각 열차에 대해 `SeoulTrainStopRepository.getDestinationStopStatus`를 호출한다.
3. 시간표 판정 결과를 `TrainArrival.destinationStopStatus`에 복사한다.
4. `ArrivalScreen`과 `ArrivalCard`가 그 상태를 초록·빨강·기본색으로 변환한다.

이 흐름에는 다음 두 가지 실패 은폐 지점이 있다.

- 출발역 시간표에서 같은 열차번호를 찾지 못하면 이유 없이 `UNKNOWN`을 반환한다.
- 시간표 API 호출, 파싱 또는 기타 예외가 발생하면 `SeoulArrivalRepository`가 예외를 모두 `UNKNOWN`으로 바꾸며 원인이나 로그를 보존하지 않는다.

반대로 출발역 열차는 찾았지만 목적지역 열차를 찾지 못하면 즉시 `DOES_NOT_STOP`으로 판정한다. 시간표 응답이 불완전한 경우에도 빨간 카드가 될 수 있으므로 안전성 측면의 별도 위험이다.

## 3. 실제 API 대조 결과

### 3.1 검증 방식과 비밀정보 처리

- 로컬 `local.properties`에 설정된 키를 메모리에서 읽어 서울시 공식 API에만 전송했다.
- 키, 키가 포함된 URL, 원본 응답 및 실제 열차번호는 터미널 출력·파일·문서에 저장하지 않았다.
- 아래에는 조회 시각, 서비스 결과 코드, 행 수, 정확 일치 건수, 시간 파싱 가능 여부만 기록한다.
- 공식 명세에서 `searchDt`는 선택 인자이며, “검색일시를 기준으로 유효한 시간표를 반환”한다고 설명한다.

### 3.2 독산 → 종로3가

2026-09-19 13:22:59 KST 조회에서 실시간 API는 `INFO-000`과 1호선 상행 4건을 반환했다. 선택한 실제 열차에 앱과 동일한 시간표 요청을 적용한 결과는 다음과 같았다.

| 조회역 | 시간표 서비스 코드 | `totalCount` | 열차번호·역 정확 일치 | 파싱 가능한 시각 |
| --- | ---: | ---: | ---: | ---: |
| 독산 | `00` | 0 | 0 | 0 |
| 종로3가 | `00` | 0 | 0 | 0 |

2026-09-19 13:26:25 KST 재조회에서는 상행 실시간 열차가 3건이었다. 세 열차 모두 `searchDt` 포함 여부와 관계없이 독산과 종로3가 시간표가 0건이었다. 즉, 독산 경로는 검색일시 문제를 제거해도 현재 실시간 열차번호를 새 시간표 API에서 매칭할 수 없다.

이 결과만으로 서울교통공사 API의 전체 제공 범위를 단정할 수는 없지만, 독산 1호선 실시간 데이터와 시간표 데이터 사이의 제공 범위 또는 열차번호 체계가 호환되지 않는다는 사실은 확인되었다.

### 3.3 서울교통공사 운영 구간 비교

2026-09-19 13:25:31 KST에 강남역 2호선 외선의 실제 열차 한 건으로 조건을 단계적으로 추가했다.

| 시간표 조건 | `totalCount` | 실제 열차번호 일치 | 강남역 일치 |
| --- | ---: | ---: | ---: |
| 필수 인자만 | 9,561 | 첫 100건에서 0 | 4 |
| 열차번호 추가 | 44 | 44 | 1 |
| 열차번호 + 강남역 | 1 | 1 | 1 |
| 앱과 동일하게 `searchDt` 추가 | 0 | 0 | 0 |

같은 열차를 `searchDt` 없이 강남과 잠실에서 다시 조회한 결과 양쪽 모두 정확한 열차번호와 파싱 가능한 출·도착 시각이 확인되었다.

| 조회역 | `totalCount` | 정확한 열차번호 일치 | 출발시각 보유 | 도착시각 보유 |
| --- | ---: | ---: | ---: | ---: |
| 강남 | 1 | 1 | 1 | 1 |
| 잠실 | 3 | 3 | 3 | 3 |

강남 행의 유효 시작일은 `2025-05-01 05:00:00`, 유효 종료일은 빈 값이었지만 2026-09-19 검색일시를 넣으면 0건이 되었다. 현재 앱의 URL 인자 순서는 공식 명세와 일치하므로, `searchDt`에 대한 공급자 데이터/필터 동작과 앱의 현재 날짜 조합이 결과를 소거하는 것으로 확인된다.

## 4. 원인 판정

### 확정 원인

1. **시간표 판정이 `UNKNOWN`이 되어 기본색으로 표시된다.** 카드 색상 코드가 실행되지 않는 것이 아니라 입력 상태가 확정되지 않는다.
2. **앱이 추가하는 현재 `searchDt`가 유효한 2호선 실제 시간표 결과를 1건에서 0건으로 만든다.** 그 결과 출발역 매칭 실패 경로를 타고 `UNKNOWN`이 된다.
3. **시간표 실패 원인이 손실된다.** API 예외는 모두 `UNKNOWN`으로 축약되고, 빈 응답과 번호 불일치도 사용자와 개발자가 구분할 수 없다.
4. **디버그 상태가 테스트 카드뿐 아니라 실제 카드와 화면 배경도 덮어쓴다.** 디버그 버튼을 사용하면 각 실제 열차의 판정 결과를 관찰할 수 없다.

### 유력 원인

- 독산 1호선은 실시간 열차가 존재해도 시간표 API에서 동일 열차번호를 양쪽 역 모두 찾지 못한다. 서울교통공사와 코레일 구간 사이의 제공 범위 또는 열차번호 체계 차이가 유력하다.

### 추가 검증 필요

- `searchDt`가 빈 유효 종료일을 가진 모든 행을 제거하는 공급자 문제인지, 허용 날짜 범위나 별도 형식 제약이 있는지 확인이 필요하다.
- 독산 1호선의 열차번호가 다른 필드 또는 연결열차번호로 제공되는지, 해당 역이 시간표 데이터셋 지원 범위에 포함되는지 공급자 명세/문의로 확인해야 한다.
- 실제 기기에서 동적 색상, 다크 모드, 빨강 점멸의 명암 대비와 화면·첫 카드 동기화는 아직 검증하지 않았다.

## 5. 영향 범위

- `searchDt`가 결과를 소거하는 노선에서는 종착역과 목적지가 정확히 같은 예외 케이스를 제외하고 대부분 기본색 카드가 된다.
- 독산과 같이 시간표 열차번호 매칭이 되지 않는 구간은 `searchDt`를 제거해도 기본색이 유지된다.
- 출발역만 매칭되고 목적지역이 누락된 불완전 응답은 빨간 미정차 카드로 오판할 수 있다.
- 디버그 빌드에서 색상 테스트 버튼을 누르면 모든 실제 카드가 같은 상태로 바뀌어 실제 데이터 결함을 가린다.

## 6. 권고 수정안과 우선순위

1. **P0 — `searchDt` 처리 수정 및 회귀 테스트**
   - 공급자 동작이 확인될 때까지 `searchDt`를 생략하거나, 지원되는 날짜/형식을 확정한 뒤에만 전달한다.
   - 동일 시간표 행이 `searchDt` 유무에 따라 사라지는 fixture와 실제 계약 테스트를 추가한다.
2. **P0 — 판정 결과에 실패 사유 보존**
   - 단일 `UNKNOWN` 대신 키 누락, 미지원 노선, API 오류, 빈 응답, 출발역 번호 불일치, 시각 해석 실패를 내부 원인으로 구분한다.
   - 개별 열차 오류는 목록 전체를 실패시키지 않되 로그와 사용자용 “확인 불가” 안내를 남긴다.
3. **P0 — 빈 목적지역 응답의 안전한 처리**
   - 응답 완전성이 입증되지 않은 경우 `DOES_NOT_STOP`으로 확정하지 말고 이유 있는 확인 불가로 처리한다.
4. **P1 — 독산/코레일 구간 매칭 전략 결정**
   - 공식 제공 범위와 열차번호 대응 근거를 확보한다. 확보할 수 없으면 지원 구간을 명시하고 정차 판정을 다른 데이터 소스로 보완한다.
5. **P1 — 디버그 상태 격리**
   - 테스트 버튼은 고정 테스트 카드에만 적용하고 실제 카드와 화면 배경은 실제 상태를 유지한다.
6. **P1 — UI 색상 검증 강화**
   - 테스트 태그뿐 아니라 Semantics에 노출한 상태/색상 토큰 또는 캡처 기반 검증으로 실제 `containerColor`를 확인한다.
